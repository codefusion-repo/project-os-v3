## Gate procedure

1. Call health, sandbox_read and sandbox_write; initially write must return BLOCKED.
2. In a separate local terminal, set STATE to the exact private directory printed during setup. Run `(umask 077; touch "$STATE/allow-probe-write")` to enable the fixed write.
3. Call sandbox_write twice: first creates the marker, second is a replay. Read it back.
4. Stop the tunnel with Ctrl-C and restart with the same directory. Read again to verify persistence.
5. Remove only the opt-in flag with `rm -- "$STATE/allow-probe-write"`. Verify write is blocked and the existing marker remains.
6. Stop the tunnel to disable all access. Keep disposable evidence until reviewed.

No arbitrary caller paths or commands. Apply the controls relevant to each operation.

## Hash-verified Linux/WSL installation

The committed runtime lock contains the 31 wheel SHA-256 hashes observed in CI job 138606270522 (Linux x86_64 CPython 3.12). That job installed the downloaded wheels in a fresh venv using hash checks and no index, passed pip check, and pip-audit 2.10.1 reported no known vulnerabilities at scan time. The build backend lock records setuptools 84.2.1, whose wheel hash, offline build and audit passed in CI job 138626336009. The installer verifies both locks and builds without index access or build isolation. CI runtime hash checks remain enforced. This is dependency reproducibility, not a guarantee of byte-identical project wheels or a pinned Python/OS toolchain. The installer creates a venv without ensurepip and verifies the exact pip 26.3 wheel from PyPI against requirements-bootstrap.lock before importing it. Package acquisition uses a private temporary wheelhouse, a clean environment and explicit index; installs of locked wheels are offline. The project builds/tests from the reviewed Git tree, not ignored checkout files. CI inventories pip's declared vendored packages and audits them separately; a successful install alone does not certify them. Host Python, OS/curl/CA trust, tunnel binary and audit-tool dependencies remain outside this dependency-audit evidence. The public install/upgrade coordinator checks every lexical interpreter ancestor and each directory/file symlink destination, ownership, permissions and executable identity before starting a transaction; use a trusted host Python 3.12 (Ubuntu 24.04 system Python in the probe CI), not a group-writable toolcache. System directory aliases are allowed only through trusted components; directory links inside the venv and parent traversal are refused. A root-owned sticky ancestor of the canonical private venv is permitted only when each existing child is independently trusted-owned; this exception does not apply to host interpreter paths. The coordinator revalidates the preflight identity and running executable before passing the canonical path to the worker, which checks its actual executable against the expected identity before build writes. Worker build success is provisional; only the coordinator reports installation success after validating the installed identity/receipt and clearing the active journal. No automatic lock regeneration.

### Single-installation maintenance

Authenticated `health` reports `installation.status=receipt_observed` with the local receipt's `sha` and `wheel_sha256` in a non-fixture runtime (not an attestation of installed files). Missing or invalid receipts report `unavailable`. [#48](https://github.com/codefusion-repo/project-os-v3/issues/48) adds an opt-in remote wrapper around the same maintenance procedure.

#### Browser maintenance (opt-in)

Only after review, integration, installation, applicable host/transport controls (including the [bounded NET-05 disposition](WSL-VALIDATION.md#finite-network-acceptance-and-evidence-reuse)) and maintenance preconditions for explicitly authorized dogfood, the local operator may create the empty owner-private `state/allow-remote-maintenance` marker (mode 0600) in the exact existing instance. Do not enable it in a fixture profile or alongside an independent maintenance operator. No new credentials, server, tunnel, host privileges or GitHub write access. Require successful operational validation before routine use. Enrolment is local once while authorization and applicability remain valid; normal remote maintenance rechecks operation-specific preflight automatically and does not require a local agent for each request. Removing that marker revokes new maintenance requests, including status; the global authenticated marker remains required. Before an accepted request starts mutation the runner rechecks admission. Once quiescing begins, allow the exact operation to finish or recover locally; do not concurrently change grants, markers, checkout, unit, audit or runtime.

- `maintenance_update(expected_sha, target_sha, wheel_sha256, ci_run_id, request_key)`: use the observed installed SHA, current canonical main SHA, independently reviewed CI wheel digest and successful push run ID. The runner reuses the GitHubReader authenticated CLI transport and existing owner-private `github-context-gh` profile to verify the canonical GitHub run identity, effective required checks from the same suite, main and Git ancestry. The existing credential must have effective read access to the canonical repository's Actions, checks, refs and branch rules. No personal credential, anonymous fallback or permission expansion is automatic. Missing config, authorization failure or exhausted authenticated quota blocks before quiescence with a sanitized code; do not retry automatically. Verify the five existing approval reads with that profile locally before the first cutover; if permissions are insufficient, stop and report the exact missing read. Before quiescing, the runner verifies the operator's digest against the unique non-expired `maintenance-wheel-<run_attempt>-<wheel_sha256>` artifact metadata of that exact successful run and main SHA. The probe publishes this name from the validated install receipt after its existing tests. No ZIP download or CI log parsing is needed; no new credential is needed if the existing dedicated profile has sufficient permissions; the artifact ZIP digest is not the wheel digest. Missing, expired, ambiguous or mismatched evidence blocks without stopping the service. The existing installer independently checks the same digest against both builds. Only reviewed canonical main is trusted executable source. No caller paths or commands.
- `maintenance_status(request_key)`: reuses the exact stable key; returns ACCEPTED/RUNNING, SUCCEEDED, BLOCKED, LOCAL_RECOVERY_REQUIRED or NOT_FOUND. SUCCEEDED means receipt, local TLS metadata and anonymous 401 verified and original opt-ins restored, not verified remote tunnel/OAuth readiness. Compare health after reconnection. Never treat timeout or missing reply as permission to resubmit under a new key.
- `maintenance_rollback(expected_sha, target_sha, wheel_sha256, request_key)`: select only the retained immediate predecessor, with its independently reviewed receipt/digest and compatible maintenance API. It preserves the reviewed checkout and delegates physical restore, release and identity checks to the existing coordinator. Older or API-incompatible predecessors, unresolved transactions, or reapplying a rolled-back SHA with a retained conflicting transaction require the local procedure below.

The one-shot user systemd service runs host Python outside the MCP service and survives the Bridge stop by design. It persists request/stage/result under the private instance `service/maintenance/`; request keys are hashed. Local commands and API calls are bounded; no raw logs returned. This is not a second queue or server. No automatic retries. Failed maintenance requests persist a fixed diagnostic step, error code and optional numeric exit/status code in a private per-request diagnostic file alongside the existing maintenance record; authenticated status returns it only when the state, stage and transition timestamp match. Old records remain readable without retroactively inferring their cause. The transient runner emits only fixed check outcomes to the existing user journal; raw command output, arguments and exception messages are not logged. The authoritative maintenance record retains its previous exact schema, so older rollback runtimes can read state and history without understanding the optional diagnostic file. Preserve that file alongside the request history; the old runtime does not expose it. An interrupted or failed diagnostic write cannot invent a diagnosis or change the maintenance outcome. Workspace/QA job evidence records known failure codes and execution phase; authorized QA delivery status returns a fixed failure code, without disclosing private file identity through generic evidence. The installed API disappears while the service is stopped; consult status when it returns. On failure before mutation, BLOCKED is terminal. On interruption, ACCEPTED/RUNNING may remain unconfirmed; after partial mutation LOCAL_RECOVERY_REQUIRED preserves evidence, with no guessed rollback or automatic second restart. The existing local runbook remains the recovery channel.

For local recovery, first revoke the maintenance marker and inspect the exact transient unit `project-os-bridge-maintenance.service` and existing coordinator journal, verify no writers/jobs or competing processes, and reconcile the checkout, receipt, unit, rollback and authorized opt-ins using the procedure below. Do not remove the journal. Only after locally verifying that no transient unit or operation remains and the installation is reconciled, preserve `service/maintenance/active.json` intact under the same private directory as `<request.id>.json` (no overwrite, with directory fsync); the original request remains queryable without replay, even if it was unconfirmed. Re-enroll the maintenance marker only after explicit local recovery. No new maintenance operation may bypass an unresolved active record.
