# Project OS Local Bridge

Optional single-user, self-hosted runtime. Browser Chat executes authorized GitHub operations directly and uses the bridge for registered local jobs. No automatic terminal-agent/Codex delegation. Read [MVP](MVP.md) for the current capability contract, [SECURITY](SECURITY.md) for gates and [WORKOS](WORKOS.md) for private OAuth setup.

Historical B0 bootstrap. Stdio mode exposes only a fixed disposable SQLite marker over stdio MCP. It is NOT the completed remote development MVP. No caller identity is verified by this probe; do not expose real repositories, credentials, shell, builds or devices with it. Only use with the PM's dedicated tunnel and restricted caller access. The local opt-in authorizes this fixed probe operation, not arbitrary remote callers or other resources. A process running as the same OS user is outside this probe's trust boundary.

## Install in WSL

Use the [hash-verified installer](#hash-verified-linuxwsl-installation) for the initial clean installation of the explicitly reviewed full SHA. For later updates retain the original checkout and follow [single-installation maintenance](#single-installation-maintenance); never use the old unlocked pip procedure or overwrite an active venv. For independent readiness follow [WSL-VALIDATION.md](WSL-VALIDATION.md). Do not use sudo for the bridge.

The remaining B0 commands below are historical disposable stdio instructions, not the recommended authenticated startup path. For a new instance use the initializer and the independent HTTPS runbook.

Create a dedicated disposable state directory outside Git:

```bash
umask 077
STATE="$(mktemp -d "$HOME/.project-os-probe.XXXXXXXX")"
printf '%s\n' "$STATE"
```

Keep the path for restart. The stdio child is launched with an empty inherited environment except for PATH; this reduces accidental credential inheritance but does not isolate same-user processes. Use the existing tunnel runtime key and ID, entered interactively; stop the previous embedded demo first. Use absolute paths without whitespace for this bootstrap command (the tunnel parses the command string). Do not place credentials in command arguments or logs.

```bash
BRIDGE="$PWD/local-bridge/.venv/bin/project-os-bridge"
read -rp "Tunnel ID: " CONTROL_PLANE_TUNNEL_ID
read -rsp "Runtime key: " CONTROL_PLANE_API_KEY

tunnel-client run --mcp.command "/usr/bin/env -i PATH=/usr/bin:/bin $BRIDGE --state-dir $STATE" --health.listen-addr 127.0.0.1:0 --health.url-file "$STATE/health.url"
unset CONTROL_PLANE_API_KEY
```

## Gate procedure

1. Call health, sandbox_read and sandbox_write; initially write must return BLOCKED.
2. In a separate local terminal, set STATE to the exact private directory printed during setup. Run `(umask 077; touch "$STATE/allow-probe-write")` to enable the fixed write.
3. Call sandbox_write twice: first creates the marker, second is a replay. Read it back.
4. Stop the tunnel with Ctrl-C and restart with the same directory. Read again to verify persistence.
5. Remove only the opt-in flag with `rm -- "$STATE/allow-probe-write"`. Verify write is blocked and the existing marker remains.
6. Stop the tunnel to disable all access. Keep disposable evidence until reviewed.

No tool accepts an arbitrary path, command, marker, or authorization flag. The local directory and flag must be owned by the service user and private. This is not an isolation mechanism for untrusted repository execution. Before enabling real resources, demonstrate caller authentication, scoped policies, credential separation and the applicable capability gates in SECURITY.md; execution isolation is mandatory for execution profiles, not bounded read-only context.

## Local vertical workflow and preflight

The disposable Git workflow can run via a dedicated local CLI state or the authenticated HTTP service with an explicit local fixture-image and Podman context opt-in. Keep those state directories separate. Use the preflight inventory without starting devices or inspecting credentials:

```bash
bash local-bridge/scripts/preflight.sh
```

Availability is not authorization or isolation evidence. Prepare a private context and import the exact audited local OCI layout using [section 4](OCI-LOCAL-VALIDATION.md#4-import-audited-bytes-and-execute-only-the-fixed-fixture-separate-permission) after its separate authorization. The worker accepts the pinned image in that context and has no automatic pull or host execution fallback.

```bash
umask 077
FIXTURE_STATE="$(mktemp -d "$HOME/.project-os-fixture.XXXXXXXX")"
read -rp "Approved local Python image with digest: " IMAGE
local-bridge/.venv/bin/project-os-bridge-fixture --state-dir "$FIXTURE_STATE" --request-key first --image "$IMAGE" --podman-context "$PODMAN_CONTEXT"
```

Keep the state directory private. Reusing the same request key retrieves the original job result; a new key creates a new fixture. Interrupted jobs are not replayed automatically. Evidence includes state transitions, Git HEAD, content digests, staged diff and validation outcome. A blocked isolation profile is not a successful validation. Unit tests exercise real Git and mock the container boundary; the actual container must be tested separately. The HTTP worker checks local authorization before each claim and again before dispatch; a claimed job denied at that boundary is BLOCKED and remaining queued jobs are preserved. In-flight operations are not cancelled. An exclusive per-state HTTP service lock prevents concurrent HTTP instances even on different ports. The worker waits for successful listener startup before claiming jobs. Only contention on the worker lock is recoverable; an unexpected worker infrastructure failure requests HTTP shutdown and exits unsuccessfully rather than leaving a ready server with a dead worker. The supervisor then stops the tunnel; interrupted work is not automatically retried. No adopted repos or real GitHub calls are enabled.

## Hash-verified Linux/WSL installation

The committed runtime lock contains the 31 wheel SHA-256 hashes observed in CI job 138606270522 (Linux x86_64 CPython 3.12). That job installed the downloaded wheels in a fresh venv using hash checks and no index, passed pip check, and pip-audit 2.10.1 reported no known vulnerabilities at scan time. The build backend lock records setuptools 84.2.1, whose wheel hash, offline build and audit passed in CI job 138626336009. The installer verifies both locks and builds without index access or build isolation. CI runtime hash checks remain enforced. This is dependency reproducibility, not a guarantee of byte-identical project wheels or a pinned Python/OS toolchain. The installer creates a venv without ensurepip and verifies the exact pip 26.3 wheel from PyPI against requirements-bootstrap.lock before importing it. Package acquisition uses a private temporary wheelhouse, a clean environment and explicit index; installs of locked wheels are offline. The project builds/tests from the reviewed Git tree, not ignored checkout files. CI inventories pip's declared vendored packages and audits them separately; a successful install alone does not certify them. Host Python, OS/curl/CA trust, OCI image, tunnel binary and audit-tool dependencies remain outside this dependency-audit evidence. The public install/upgrade coordinator checks every lexical interpreter ancestor and each directory/file symlink destination, ownership, permissions and executable identity before starting a transaction; use a trusted host Python 3.12 (Ubuntu 24.04 system Python in the probe CI), not a group-writable toolcache. System directory aliases are allowed only through trusted components; directory links inside the venv and parent traversal are refused. A root-owned sticky ancestor of the canonical private venv is permitted only when each existing child is independently trusted-owned; this exception does not apply to host interpreter paths. The coordinator revalidates the preflight identity and running executable before passing the canonical path to the worker, which checks its actual executable against the expected identity before build writes. Worker build success is provisional; only the coordinator reports installation success after validating the installed identity/receipt and clearing the active journal. No automatic lock regeneration.

In a clean independent checkout of the explicitly reviewed full commit, run `bash local-bridge/scripts/install.sh REVIEWED_FULL_SHA`. Existing venvs are preserved; partial new installation is retained, not automatically removed. From Windows, the matching PowerShell wrapper accepts ReviewedSha, Distribution and the absolute Linux Checkout path and delegates to the same WSL installer. ### Single-installation maintenance

Authenticated `health` reports `installation.status=receipt_observed` with the local receipt's `sha` and `wheel_sha256` in a non-fixture runtime (not an attestation of installed files). Missing or invalid receipts report `unavailable`. [#48](https://github.com/codefusion-repo/project-os-v3/issues/48) adds an opt-in remote wrapper around the same maintenance procedure.

#### Browser maintenance (opt-in)

Only after review, integration, installation, applicable host/transport controls (including the [bounded NET-05 disposition](WSL-VALIDATION.md#finite-network-acceptance-and-evidence-reuse)) and maintenance preconditions for explicitly authorized dogfood, the local operator may create the empty owner-private `state/allow-remote-maintenance` marker (mode 0600) in the exact existing instance. Do not enable it in a fixture profile or alongside an independent maintenance operator. No new credentials, server, tunnel, host privileges or GitHub write access. Require successful operational validation before routine use. Enrolment is local once while authorization and applicability remain valid; normal remote maintenance rechecks operation-specific preflight automatically and does not require a local agent for each request. Removing that marker revokes new maintenance requests, including status; the global authenticated marker remains required. Before an accepted request starts mutation the runner rechecks admission. Once quiescing begins, allow the exact operation to finish or recover locally; do not concurrently change grants, markers, checkout, unit, audit or runtime.

- `maintenance_update(expected_sha, target_sha, wheel_sha256, ci_run_id, request_key)`: use the observed installed SHA, current canonical main SHA, independently reviewed CI wheel digest and successful push run ID. The runner verifies public GitHub run identity, effective required checks from the same suite, main and Git ancestry. Before quiescing, the runner verifies the operator's digest against the unique non-expired `maintenance-wheel-<run_attempt>-<wheel_sha256>` artifact metadata of that exact successful run and main SHA. The probe publishes this name from the validated install receipt after its existing tests. No ZIP download, CI log parsing or new credentials are needed; the artifact ZIP digest is not the wheel digest. Missing, expired, ambiguous or mismatched evidence blocks without stopping the service. The existing installer independently checks the same digest against both builds. Only reviewed canonical main is trusted executable source. No caller paths or commands.
- `maintenance_status(request_key)`: reuses the exact stable key; returns ACCEPTED/RUNNING, SUCCEEDED, BLOCKED, LOCAL_RECOVERY_REQUIRED or NOT_FOUND. SUCCEEDED means receipt, local TLS metadata and anonymous 401 verified and original opt-ins restored, not verified remote tunnel/OAuth readiness. Compare health after reconnection. Never treat timeout or missing reply as permission to resubmit under a new key.
- `maintenance_rollback(expected_sha, target_sha, wheel_sha256, request_key)`: select only the retained immediate predecessor, with its independently reviewed receipt/digest and compatible maintenance API. It preserves the reviewed checkout and delegates physical restore, release and identity checks to the existing coordinator. Older or API-incompatible predecessors, unresolved transactions, or reapplying a rolled-back SHA with a retained conflicting transaction require the local procedure below.

The one-shot user systemd service runs host Python outside the MCP service and survives the Bridge stop by design. It persists request/stage/result under the private instance `service/maintenance/`; request keys are hashed. Local commands and API calls are bounded; no raw logs returned. This is not a second queue or server. No automatic retries. The installed API disappears while the service is stopped; consult status when it returns. On failure before mutation, BLOCKED is terminal. On interruption, ACCEPTED/RUNNING may remain unconfirmed; after partial mutation LOCAL_RECOVERY_REQUIRED preserves evidence, with no guessed rollback or automatic second restart. The existing local runbook remains the recovery channel.

For local recovery, first revoke the maintenance marker and inspect the exact transient unit `project-os-bridge-maintenance.service` and existing coordinator journal, verify no writers/jobs or competing processes, and reconcile the checkout, receipt, unit, rollback and authorized opt-ins using the procedure below. Do not remove the journal. Only after locally verifying that no transient unit or operation remains and the installation is reconciled, preserve `service/maintenance/active.json` intact under the same private directory as `<request.id>.json` (no overwrite, with directory fsync); the original request remains queryable without replay, even if it was unconfirmed. Re-enroll the maintenance marker only after explicit local recovery. No new maintenance operation may bypass an unresolved active record.
