# Project OS Local Bridge

Optional single-user, self-hosted runtime. Browser Chat executes authorized GitHub operations directly and uses the bridge for registered local jobs. No automatic terminal-agent/Codex delegation. Read [MVP](MVP.md) for the current capability contract, [SECURITY](SECURITY.md) for gates and [WORKOS](WORKOS.md) for private OAuth setup.

Historical B0 bootstrap. Stdio mode exposes only a fixed disposable SQLite marker over stdio MCP. It is NOT the completed remote development MVP. No caller identity is verified by this probe; do not expose real repositories, credentials, shell, builds or devices with it. Only use with the PM's dedicated tunnel and restricted caller access. The local opt-in authorizes this fixed probe operation, not arbitrary remote callers or other resources. A process running as the same OS user is outside this probe's trust boundary.

## Gate procedure

1. Call health, sandbox_read and sandbox_write; initially write must return BLOCKED.
2. In a separate local terminal, set STATE to the exact private directory printed during setup. Run `(umask 077; touch "$STATE/allow-probe-write")` to enable the fixed write.
3. Call sandbox_write twice: first creates the marker, second is a replay. Read it back.
4. Stop the tunnel with Ctrl-C and restart with the same directory. Read again to verify persistence.
5. Remove only the opt-in flag with `rm -- "$STATE/allow-probe-write"`. Verify write is blocked and the existing marker remains.
6. Stop the tunnel to disable all access. Keep disposable evidence until reviewed.

No tool accepts an arbitrary path, command, marker, or authorization flag. The local directory and flag must be owned by the service user and private. This is not an isolation mechanism for untrusted repository execution. Before enabling real resources, demonstrate caller authentication, scoped policies, credential separation and execution isolation.

## Local vertical workflow and preflight

The disposable Git workflow can run via a dedicated local CLI state or the authenticated HTTP service with an explicit local fixture-image and Podman context opt-in. Keep those state directories separate. Use the preflight inventory without starting devices or inspecting credentials:

```bash
bash local-bridge/scripts/preflight.sh
```

Availability is not authorization or isolation evidence. Prepare a private context and import the exact audited local OCI layout using [section 4](OCI-LOCAL-VALIDATION.md#4-import-audited-bytes-and-execute-only-the-fixed-fixture-separate-permission) after its separate authorization. The worker accepts the pinned image in that context and has no automatic pull or host execution fallback.

```bash
umask 077
FIXTURE_STATE="$(mktemp -d "$HOME/.project-os-fixture.XXXXXXXX")"
read -rp "Approved local Python image with digest: " IMAGE
local-bridge/.venv/bin/project-os-bridge-fixture --state-dir "$FIXTURE_STATE" --request-key first --image "$IMAGE" --podman-context "$PODMAN_CONTEXT"
```

Keep the state directory private. Reusing the same request key retrieves the original job result; a new key creates a new fixture. Interrupted jobs are not replayed automatically. Evidence includes state transitions, Git HEAD, content digests, staged diff and validation outcome. A blocked isolation profile is not a successful validation. Unit tests exercise real Git and mock the container boundary; the actual container must be tested separately. The HTTP worker checks local authorization before each claim and again before dispatch; a claimed job denied at that boundary is BLOCKED and remaining queued jobs are preserved. In-flight operations are not cancelled. An exclusive per-state HTTP service lock prevents concurrent HTTP instances even on different ports. The worker waits for successful listener startup before claiming jobs. Only contention on the worker lock is recoverable; an unexpected worker infrastructure failure requests HTTP shutdown and exits unsuccessfully rather than leaving a ready server with a dead worker. The supervisor then stops the tunnel; interrupted work is not automatically retried. No adopted repos or real GitHub calls are enabled.

The committed runtime lock contains the 31 wheel SHA-256 hashes observed in CI job 138606270522 (Linux x86_64 CPython 3.12). That job installed the downloaded wheels in a fresh venv using hash checks and no index, passed pip check, and pip-audit 2.10.1 reported no known vulnerabilities at scan time. The build backend lock records setuptools 84.2.1, whose wheel hash, offline build and audit passed in CI job 138626336009. The installer verifies both locks and builds without index access or build isolation. CI runtime hash checks remain enforced. This is dependency reproducibility, not a guarantee of byte-identical project wheels or a pinned Python/OS toolchain. The installer creates a venv without ensurepip and verifies the exact pip 26.3 wheel from PyPI against requirements-bootstrap.lock before importing it. Package acquisition uses a private temporary wheelhouse, a clean environment and explicit index; installs of locked wheels are offline. The project builds/tests from the reviewed Git tree, not ignored checkout files. CI inventories pip's declared vendored packages and audits them separately; a successful install alone does not certify them. Host Python, OS/curl/CA trust, OCI image, tunnel binary and audit-tool dependencies remain outside this dependency-audit evidence. The public install/upgrade coordinator checks every lexical interpreter ancestor and each directory/file symlink destination, ownership, permissions and executable identity before starting a transaction; use a trusted host Python 3.12 (Ubuntu 24.04 system Python in the probe CI), not a group-writable toolcache. System directory aliases are allowed only through trusted components; directory links inside the venv and parent traversal are refused. A root-owned sticky ancestor of the canonical private venv is permitted only when each existing child is independently trusted-owned; this exception does not apply to host interpreter paths. The coordinator revalidates the preflight identity and running executable before passing the canonical path to the worker, which checks its actual executable against the expected identity before build writes. Worker build success is provisional; only the coordinator reports installation success after validating the installed identity/receipt and clearing the active journal. No automatic lock regeneration.

### Single-installation maintenance

[Decision LB28-20261125-SINGLE-INSTALLATION-01](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7159966742) supersedes separate-checkout updates, not the initial independent certification, security gates or rollback requirements. Keep the original central checkout and local-bridge/.venv at stable paths. The selector, first-install script and PowerShell wrapper do not implicitly upgrade an existing Bridge. On Windows run maintenance inside the same dedicated WSL distribution.

1. Verify the target integrated SHA, all applicable post-merge CI checks, wheel SHA-256, prior installed runtime evidence and host trust. Inspect the original checkout and redundant checkout privately: canonical origin, ownership, clean Git status, worktrees, all refs/commits, ignored files and launcher bindings. Preserve any unknown or unique data; no reset/clean or destructive checkout. State and credentials must remain outside Git. No concurrent operator, install, direct service launch or Git operation. Do not run from the venv being replaced.
2. Using the currently bound reviewed runtime, verify the exact unit and jobs, revoke only the authorized empty opt-ins, ensure no fixture binding, stop quiescently and verify no workers/tunnel/pending jobs/effects remain. Preserve the exact unit and audit/SQLite baseline. During consolidation the bound Python may be in the redundant checkout, which must remain available until cutover and rollback validation. Keep the same instance root.
3. Advance the original clean checkout to the exact reviewed integrated SHA (verify origin and ancestry, no overwrite of ignored files; preserve any local branches). For a central checkout on main use the reviewed top-level installer without provider mode to fast-forward, after checking its launcher identity; for a detached Bridge checkout use git fetch, verify target ancestry and git checkout --detach --no-overwrite-ignore at the exact reviewed SHA. Do not infer the installed runtime SHA from Git HEAD.
4. Run from the original checkout with host Python 3.12 and the exact already bound Python path. The upgrade checks the canonical checkout, exact stopped linked disabled unit, lifecycle/supervisor/HTTP/worker locks, absent opt-ins and read-only SQLite for pending/unknown jobs and unresolved effects across all principals. An ambiguous state blocks. The operator still must verify no other instance/process uses the venv and no competing tunnel session exists. No service/credential/state migration, automatic start, or rebind.
   
   ```bash
   python3 -I local-bridge/scripts/upgrade.py fence "$REVIEWED_SHA" \
     --root "$ROOT" --bound-python "$BOUND_PYTHON"

   python3 -I local-bridge/scripts/upgrade.py upgrade "$REVIEWED_SHA" \
     --root "$ROOT" --bound-python "$BOUND_PYTHON" --expected-wheel "$EXPECTED_WHEEL_SHA256" \
     --previous-sha "$PREVIOUS_SHA" --previous-wheel "$PREVIOUS_WHEEL_SHA256"
   ```
   
   The explicit fence atomically replaces only the exact prepared stopped unit with a maintenance definition, preserves its bound Python identity in a comment, sets RefuseManualStart=yes and replaces ExecStart with /usr/bin/false. The user manager must reload and report the fence effective, with no drop-ins or pending jobs. The legacy controller rejects the changed unit definition; dependency activation cannot execute Bridge. The fence persists across interruptions and reboots, even when all locks disappear. Do not invoke the supervisor directly or edit/rebind the unit during maintenance. The fence action can reconcile an interrupted reload. No venv mutation is permitted without the loaded fence.

   For normal maintenance the previous SHA/wheel must match its existing installation receipt and exact bound path. For the one-time consolidation of a receipt-less original, add `--legacy-consolidation` only after independently verifying the currently bound, separate certified runtime's SHA, wheel and install evidence. Supply that runtime's SHA/wheel as previous values. The original legacy environment is a physical quarantine, not a certified fallback; its contents are not executed or assigned a fabricated receipt. The separately bound runtime remains the operational fallback until cutover and rollback validation. A receipt-less same-path upgrade is blocked.

   The previous venv is moved to local-bridge/.venv-install.rollback/previous (same filesystem, private); never execute it there. A clean build is installed in the original .venv path only. The installer compares two independently built wheels and the supplied CI digest before installing the project wheel, checks dependencies, runs regressions and records a local SHA/wheel receipt. On failure restore previous to the exact original path only after the recorded writer group is gone; retain the candidate, if any. A private durable transaction binds original path, old directory identity/config/receipt, interpreter identity (relative symlink chain, resolved host target, ownership, mode, inode and SHA-256), prior reviewed SHA/wheel, candidate SHA/wheel and interpreter identity, instance root, boot and writer group. The common checkout lock covers initial install, upgrade and restore, and is inherited by the build worker along with service locks. A handshake prevents writes before the writer group is recorded. A surviving process group (including reused IDs or zombies) blocks recovery; after reboot no old group survives. Reviewed build processes must stay in that group. These are coordination controls for trusted local processes, not protection against malicious same-UID code. An active transaction blocks new installation and new-runtime supervisor startup; never launch a legacy runtime directly during maintenance. A prior backup or uncertain interruption blocks another upgrade. A receipt is not proof of authenticity absent reviewed artifact evidence. Interpreter identity checks do not attest every file in the venv or host; host Python changes that alter the recorded executable or previously unrecorded directory aliases require independent reconciliation before restore. Do not rewrite an older journal to force a match.
5. After successful install, explicitly release the fence with the same currently bound Python (legacy fallback during consolidation). It requires no active journal, no surviving writers, verified candidate/previous identity for a completed transaction and a stopped fenced unit. Release changes only the maintenance definition back to its reviewed original and reloads the manager; it never starts the service. If interrupted before reload, re-establish the fence and reconcile before release. No release on ambiguous transaction or writer state.

   ```bash
   python3 -I local-bridge/scripts/upgrade.py release "$REVIEWED_SHA" \
     --root "$ROOT" --bound-python "$BOUND_PYTHON"
   ```

   Then, if consolidating, rebind only the exact reviewed unit to the original Python under lifecycle lock using the existing stopped-unit procedure and private unit backup; verify rendered definition, daemon reload and status. Normal same-path upgrades need no rebind. Start explicitly with opt-ins absent, verify process identity, listener, TLS and applicable pre-opt-in checks, then restore only previously authorized access. Preserve jobs and evidence; do not repeat completed acceptance tests simply because of installation. Do not remove the redundant checkout while any process, unit, launcher, worktree, configuration or unique data depends on it.
6. If the new runtime is unsuitable, stop and reconcile first, archive any OAuth sidecar intact per [WORKOS.md](WORKOS.md#audit-rollback-compatibility), then restore under the same maintenance guard:
   
   ```bash
   python3 -I local-bridge/scripts/upgrade.py restore "$REVIEWED_SHA" \
     --root "$ROOT" --bound-python "$BOUND_PYTHON"
   ```
   
   This restores the previous venv, not the Git checkout. If the candidate migrated a legacy GitHub profile, the same maintenance restore also reconciles that profile before moving the venv. Migration evidence is written before the first profile replacement inside the existing private rollback directory (not a live registry). Restore archives the current multi-project grants and the exact legacy-readable target there before the atomic replacement; interrupted restore accepts only the recorded source or target, refuses unrelated settings changes, and never resurrects a revoked or changed legacy grant. Unchanged, still-valid legacy binding can be retained; otherwise the old runtime starts without a real GitHub binding. Extra grants remain offline evidence, not active authorizations; re-enroll explicitly after a future upgrade. Do not remove the rollback evidence before reconciliation; the existing retention policy applies. The journal must match the reviewed target SHA and original path, no writer group may remain, and the previous inode/config/receipt must match the recorded identity. The previous reviewed SHA/wheel must still be independently verified before any use; never fall back to an uncertified pilot. For legacy consolidation, if cutover has already occurred, stop and rebind to the independently certified fallback before fencing that binding again and restoring the original. The quarantined original is not authorized for startup. After restore, release explicitly only with the verified previous binding. Do not release or start while the active journal or writers remain. Reconcile the checkout and unit explicitly. Restore can recover between candidate and previous renames or after the previous rename if identity matches; if paths or identities are ambiguous, do not retry or delete anything. For an interrupted first installation with no backup, preserve the active journal and partial venv; after independently checking the recorded boot/group and all writers, archive both offline under the checkout lock before a fresh install. Do not bypass or delete an unresolved journal. A failed build already restored automatically may retain candidate but no previous. Inspect locally before clearing the backup. No automatic cleanup.
7. After validated cutover and rollback readiness, retire only the operator-authorized redundant checkout and temporary backup. Verify all refs/worktrees and ancestry to integrated main, no local changes or unique ignored/private data, no mountpoints or external symlink targets to remove, and no launcher/unit/process references. Retain reviewed SHA/wheel/test evidence and prior artifact recovery instructions; manually remove only the verified redundant installation and temporary backup when safe. Preserve SQLite, TLS, tunnel, WorkOS and audit. If any condition cannot be verified, stop cleanup, not service certification. Future updates use the same original path.

The runtime and build-backend evidence jobs use the same verified pip bootstrap and 29-package auditor lock, with separate fresh CI environments. The non-OCI selector's optional terminal test is outside Local Bridge bootstrap scope. ### LB-06 candidate context (not enabled)

The candidate `GitHubContext` delivery boundary reuses `GitHubReader.batch_issues` and `issue_context`. The authenticated server/app builders accept an optional trusted provider for disposable tests and the gated supervised profile below. Default startup does not register the real reader. The synthetic tool remains separate.

The candidate requires the existing policy plus a trusted, current exact (principal, project, repository) grant evaluator before fetching, before and after each upstream request, and before disclosure. The authenticated tool checks caller identity, local global authorization and token expiry before and after each upstream request and again before delivery. Already dispatched requests may finish, but their results are discarded on detected revocation. It rejects arbitrary project paths, non-integer IDs and batches above five. Results project issue/comment fields, strip control characters, omit oversized text, redact recognized credential patterns and enforce a conservative 512 KiB serialized aggregate budget with omitted issue IDs and explicit incompleteness. Content is untrusted; heuristic redaction cannot guarantee arbitrary prose is secret-free. No raw response or private mapping is returned. The delivery boundary binds issue repository_url and url, and comment issue_url and url/id, to the authorized repository and issue before projection. Repository name casing is ignored, but aliases, renamed paths and noncanonical URLs are rejected; authorization must be explicitly rebound outside this candidate. A mismatched issue is discarded with RESOURCE_MISMATCH; a mismatched comment invalidates the entire comment collection.
