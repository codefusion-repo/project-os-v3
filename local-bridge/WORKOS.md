# WorkOS Connect bootstrap (Staging)

Only disposable jobs and synthetic GitHub fixtures. No adopted repos, real gh calls or execution tools. Keep identifiers local. No tokens, API keys, private signing keys or config in Git.

## Configure

For new independent validation use [WSL-VALIDATION.md](WSL-VALIDATION.md) and its private initializer/supervised HTTPS path. The plaintext commands below document the earlier staging pilot only; do not use them for a new production-readiness run. For the same operator, the existing staging identity, tunnel, restricted runtime key and OAuth connector may be retained only through the [exclusive transition](WSL-VALIDATION.md#exclusive-same-operator-staging-transition), with fresh private state, TLS, quiescence, verified scope and fresh live evidence. Do not duplicate resources or rotate uncompromised scoped keys just to repeat setup; do not inherit pilot grants or allow concurrent tunnel use.

In AuthKit Staging keep email/password and MFA enabled, public signup and unused social login disabled. Enable CIMD under Connect, leave DCR disabled. The issuer is the exact hosted AuthKit HTTPS domain from public OAuth metadata (no trailing slash). Register the exact public MCP tunnel URL as the sole Resource Indicator, not localhost or the WorkOS client ID. For the default OpenAI tunnel base the documented candidate is https://api.openai.com/v1/mcp/<tunnel_id>. Verify the actual connector URL and protected-resource metadata before granting access; this document does not attest any live tunnel. Do not configure wildcards or fallback audiences.

From the installed bridge checkout, after running its tests, create private configuration using the local shell:

```bash
umask 077
AUTH_ROOT="$(mktemp -d "$HOME/.project-os-auth.XXXXXXXX")"
mkdir -m 700 "$AUTH_ROOT/state"
export AUTH_ROOT
python3 - <<'PY'
import json, os
from pathlib import Path
root = Path(os.environ["AUTH_ROOT"])
cfg = {k: input(p).strip() for k,p in [
    ("issuer","Exact AuthKit issuer: "),
    ("resource","Exact public MCP tunnel URL: "),
    ("subject","WorkOS user ID: ")]}
with (root/"oauth.json").open("x") as f:
    json.dump(cfg,f)
PY
printf 'Private auth root: %s\n' "$AUTH_ROOT"
local-bridge/.venv/bin/project-os-bridge-http --config "$AUTH_ROOT/oauth.json" --state-dir "$AUTH_ROOT/state"
```

Keep the server terminal running. With a second terminal, check the local public metadata at http://127.0.0.1:8765/.well-known/oauth-protected-resource/mcp and confirm resource and issuer exactly match the local config. An unauthenticated MCP POST must return 401. Only after checking the metadata, enable the disposable mode with an empty owner-private file: `(umask 077; touch "$AUTH_ROOT/state/allow-authenticated-probe")` (set AUTH_ROOT to the same directory in the second terminal). Do not reuse the stdio state directory.

Stop the old tunnel process; reuse the same runtime credentials entered privately, not in arguments or chat. In a separate shell:

```bash
(
  set -euo pipefail
  read -rp "Tunnel ID: " CONTROL_PLANE_TUNNEL_ID
  read -rsp "Runtime key: " CONTROL_PLANE_API_KEY
  printf '\n'
  export CONTROL_PLANE_TUNNEL_ID CONTROL_PLANE_API_KEY
  read -rp "Private auth root: " AUTH_ROOT
  ISSUER="$(python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["issuer"])' "$AUTH_ROOT/oauth.json")"
  tunnel-client run \
    --mcp.server-url http://127.0.0.1:8765/mcp \
    --mcp.oauth-trusted-origin "$ISSUER" \
    --harpoon.allow-plaintext-http
)
```

For tunnel-client v0.0.21, the exact AuthKit origin must be trusted for OAuth discovery. The plaintext Harpoon exception is process-wide and is suitable only for the dedicated trusted loopback staging fixture; do not add other HTTP targets or use this exception for real resources. Prefer HTTPS for production. The PM observed automatic OAuth discovery after these flags were added. A new OAuth connector was needed because the previous connector was configured without authentication. Keep the old connector unused; retire it only with explicit authorization.

Configure the ChatGPT plugin for OAuth/CIMD, not no authentication. Verify the discovered resource matches exactly, authenticate in AuthKit and consent, and refresh discovery. The canonical SDK protected-resource metadata and both tunnel aliases advertise only openid. Per [MCP 2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#refresh-tokens), offline_access belongs to client/authorization-server negotiation, not resource metadata or the WWW-Authenticate scope. AuthKit advertises offline_access in its own authorization-server metadata; a client using openid must request it to obtain a refresh token. No extra local permission follows. ChatGPT owns the refresh token and its rotation; the bridge validates access tokens only. Refresh behavior is client-dependent. Never pass bearer tokens as tool arguments.

## OAuth lifecycle acceptance and recovery (#28)

Use the existing authorized supervised HTTPS instance and connector, with the reviewed runtime and unchanged private state, issuer, resource, subject, tunnel and grants. Do not create another connector or rotate credentials merely to troubleshoot. Keep fixture and real-resource access disabled.

1. Before enabling the local markers, compare the JSON documents at the canonical protected-resource path (the well-known prefix followed by the exact public resource URL path), the well-known root and its /mcp alias. All must advertise only openid, the exact same resource and issuer (including absence of a trailing issuer slash), and header bearer authentication. Check that the unauthenticated MCP response is 401 and its resource_metadata challenge resolves to the correct public metadata through the existing tunnel, without offline_access in the challenge scope. The SDK may cache public metadata for one hour; verify fresh discovery instead of assuming an existing connector has reloaded it. Do not publish private URLs or identifiers.
2. Verify the existing ChatGPT OAuth/CIMD grant privately. Check the exact configured AuthKit issuer's /.well-known/oauth-authorization-server document over HTTPS: issuer equality, scopes_supported includes openid and offline_access, and grant_types_supported includes authorization_code and refresh_token. Check the public ChatGPT client ID metadata document (https://chatgpt.com/oauth/client.json) for refresh_token in grant_types. These are capability checks, not evidence of an issued refresh token. In WorkOS, inspect whether offline_access was requested and whether refresh grants succeed, if the available provider events expose those facts. Do not extract access tokens, refresh tokens, authorization codes, cookies or private configuration. If the previous grant is confirmed to lack renewal capability, or the current refresh token is confirmed rejected with invalid_grant, reconnect the existing connector once after correcting discovery and record that intervention. Do not infer either condition from an HTTP 403 or a UI prompt alone.
3. Record a successful read-only health call and its UTC time. After the configured access-token lifetime has elapsed, repeat the read-only call without manual reconnect; do this over two renewal intervals. Establish actual refresh success with provider evidence when available. For issue #28 only, the [PM-ratified functional acceptance decision](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7172938453) permits acceptance of authenticated continuity over two intervals exceeding the verified configured access-token lifetime, without recurrent manual reconnection, with the renewal grant confirmed, correlated HTTP audit evidence, and continuity after the validated cutover. When client/provider exchange telemetry is unavailable, explicitly record that limitation: successful health calls, HTTP 200 and TOKEN_ACCEPTED do not prove the grant_type, issuance or rotation of refresh tokens. Preserve prior failures and unknown root cause; do not waive any remaining lifecycle, security or certification gates or generalize this disposition to production readiness. See [T0/T1/T2 evidence](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7159470093) and [final cutover](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7172522453).
4. Reuse prior revocation and job-count evidence from #14. If a focused post-change revocation test is needed, remove only the known empty global marker, check one authenticated read returns 403 without an OAuth challenge, restore using the existing noclobber procedure and check health without new consent. Never retry a submission of uncertain outcome. A client reconnect prompt after 403 is a client/provider interoperability finding, not permission to return 200 or weaken local authorization.
5. Follow [WSL-VALIDATION.md](WSL-VALIDATION.md) for quiescent stop/start with the same private state; compare the existing job evidence and replay the same request key only. Stop and revoke markers when done. Preserve state and logs.

Correlate UTC call times with the fixed-schema local HTTP audit and available WorkOS grant events. Report only status counts, timestamps, scope-presence booleans and sanitized error categories. A 401 can mean absent/expired/invalid access token or verifier/JWKS failure. The local private oauth-audit.jsonl stores supplemental /mcp completion observations with the exact timestamp/event/status of the corresponding unchanged security-audit.jsonl completion and one fixed auth_outcome: TOKEN_MISSING, TOKEN_MALFORMED, TOKEN_EXPIRED, TOKEN_SIGNATURE_INVALID, TOKEN_AUDIENCE_INVALID, TOKEN_CLAIMS_INVALID, JWKS_UNAVAILABLE or TOKEN_ACCEPTED. The claim-rejection refinement adds the fixed values `TOKEN_SUBJECT_INVALID`, `TOKEN_CLIENT_MISMATCH`, `TOKEN_REQUIRED_CLAIM_MISSING`, `TOKEN_FORBIDDEN_CLAIM_PRESENT`, `TOKEN_SESSION_CLAIM_INVALID`, `TOKEN_SCOPE_INVALID`, `TOKEN_TEMPORAL_CLAIM_INVALID`, `TOKEN_ISSUER_INVALID`. These identify the first classified rejection in the existing validation order; library exceptions are classified only by fixed types already in the rejection set. `TOKEN_CLAIMS_INVALID` remains valid for historical entries and unclassified failures (including ambiguous parser/type failures). The four-field sidecar schema, correlation, shared cap, primary audit, HTTP response/challenge and rollback procedure are unchanged. Readers with an exhaustive old enum must accept the additional values; never rewrite historical records or expose claim names, values, tokens or exception text. These categories do not demonstrate refresh issuance or rotation. Missing means no Authorization header; malformed includes unsupported credentials or a verifier not reached; JWKS_UNAVAILABLE includes key lookup, validation and cooldown failures, not necessarily an outage. TOKEN_ACCEPTED means JWT verification succeeded, not local authorization or successful token refresh. Metadata, admission and rate-limit records have no supplemental observation. Both active files share the existing 4 MiB cap. Admission checks both files; after verifying private metadata and the combined budget, primary completion is appended before opening or creating the supplemental file, whose observation is best effort. If the shared budget cannot be established, neither completion is appended. Fixed local warnings distinguish primary completion failure from supplemental failure without exception text. The pinned MCP SDK 2.3.0 passes HTTPStatus values through Starlette 1.10.0 ASGI response.start; the auditor accepts this standard enum and exact int only, storing plain integer statuses. Synthetic regressions trace initialize and tools/call through the real SDK stack. Read both files locally only with bounded_text and validate their fixed schemas; the remote collector reads only the unchanged primary file. Missing observations cannot be retroactively classified. Never publish raw records, token values or claims. A 403 from the local gate is authorization denial, not token expiry. If WorkOS reports invalid_grant or rotation failure, or ChatGPT prompts again despite successful refresh, stop repeated reconnections and isolate the client/provider failure before changing server policy. Do not lengthen token lifetime, bypass JWT validation or store refresh tokens in the bridge as a workaround. For ordinary clock skew the verifier uses a fixed five-second PyJWT leeway (RFC 7519 sections 4.1.5–4.1.6), then checks exp against the local clock without any grace before returning an AccessToken; the original exp is preserved and resource checks still enforce it. Only iat/nbf can be up to five seconds ahead of local time. NumericDate types, positive duration up to 3600 seconds, and all identity/signature/scope checks remain strict; nbf at or after exp is rejected. TOKEN_NOT_YET_VALID distinguishes PyJWT's immature-token rejection from other temporal errors, without values or extra audit fields. This bounded interoperability allowance does not change WorkOS TTL, prove refresh, or compensate for a materially wrong clock.

### Audit rollback compatibility

The primary security-audit.jsonl is byte-format compatible with the previous reviewed runtime; no conversion or history rewrite is needed. Before reverting the unit, remove only the authorized empty opt-in markers, stop the exact unit under the existing lifecycle procedure, verify no pending effects and record the primary HTTP counts. If oauth-audit.jsonl exists, verify it is an owner-private regular single-link file (no symlinks), validate its fixed schema and bounded size, then archive it intact in a new owner-private local directory outside active state. Use a non-overwriting move on the same filesystem; verify SHA-256 of the archived bytes equals the pre-move digest before continuing. If the file is unsafe, the archive already exists or verification fails, stop and preserve the evidence; do not delete or rewrite either file. This offline archive keeps the old runtime's primary-only 4 MiB active budget from silently excluding a retained sidecar. Do not restore an archived sidecar automatically on upgrade; preserve it as evidence. The primary file and SQLite remain in place; verify the previous runtime's audit counts match the pre-rebind baseline before restoring service access. Subsequent admissions may add primary records normally. No WorkOS consent, TLS, tunnel or credential change is required for this rollback. A missing or incomplete supplemental observation is not proof of an authentication outcome.

The regression suite uses synthetic access tokens and reconstructs the HTTP app over the same SQLite state; this is not proof of live OAuth refresh, systemd restart or tunnel behavior. Issue #28 remains open until live criteria pass.

## Evidence and stop

Local HTTP tests use generated JWTs and a mocked JWKS fetch; they do not prove live WorkOS or tunnel discovery. Check health, submit a unique disposable probe job, replay the same request key, inspect status and synthetic batch. Remove only the local opt-in file to deny subsequent requests. Missing or invalid tokens still receive HTTP 401 with an OAuth challenge; authenticated requests with the local opt-in revoked receive HTTP 403 without a WWW-Authenticate challenge. OAuth metadata remains public. Recreating the empty private flag restores access without intentionally requiring a new OAuth session. The worker checks authorization before claim and dispatch; a claimed but denied job becomes BLOCKED, while already dispatched work is not cancelled. One HTTP service per private state is allowed, and workers wait for successful listener startup. Unexpected worker infrastructure failure stops HTTP with a nonzero exit rather than silently abandoning the queue. Stop accepting requests by shutting down the server. Normal shutdown waits for an in-flight registered job and its cleanup; it does not immediately cancel work. Forced termination may leave a container or interrupted job; inspect locally before restart. The prior pilot later observed FORBIDDEN and restoration (SECURITY.md); the raw local 403 audit and aggregate job count were not independently inspected. Reverify on the independent HTTPS instance. Stop both processes with Ctrl-C to terminate access. Removing the opt-in is not revocation of WorkOS refresh tokens; revoke the WorkOS application authorization separately if required. JWKS cache TTL 300 seconds, unknown-key refresh cooldown 15 seconds; expiry and failed refresh fail closed for the requested key. No introspection. Same-user local processes are outside the trust boundary.

## Private loopback TLS (production transport prerequisite)

Use a dedicated local CA and a server certificate with IP SAN 127.0.0.1, serverAuth usage and a protected private key. Provision them outside Git under the service user's private instance directory; do not reuse the WorkOS issuer keys or install the CA globally. Keep the CA signing key offline. The server certificate and key must be canonical absolute owner-private regular files. Start the HTTP entrypoint with the existing config/state and `--tls-cert /private/server.pem --tls-key /private/server-key.pem`. Preserve the approved fixture image option if applicable. Verify locally with curl using the dedicated CA and exact loopback IP, then start tunnel-client v0.0.21 with `--mcp.server-url https://127.0.0.1:8765/mcp --ca-bundle /private/ca.pem --mcp.oauth-trusted-origin "$ISSUER"`. Do not pass the plaintext exception; ensure HARPOON_ALLOW_PLAINTEXT_HTTP is unset and no loaded config enables it. The CA bundle is additive and applies to all tunnel-client outbound TLS, not only MCP; use a dedicated narrowly controlled CA and process. Do not disable TLS validation. Recheck metadata, unauthenticated 401, live health, fixture evidence, revocation and restoration. Restart on certificate rotation. This mode is implemented but live tunnel interoperability is not yet demonstrated. No real resource grant follows from TLS alone.
