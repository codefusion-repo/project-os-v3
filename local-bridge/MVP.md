# MVP contract — one installation, one operator

> **Current product decision (2026-11-28):** [AgentsUbuntu is the sole local execution environment](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7233893145). Use the existing WSL terminal, toolchains and Jobs directly. No container backend, additional isolation infrastructure or certification. The implementation is still incomplete; this contract is not operational evidence.


Project OS is a Markdown-first coordination kit, not a SaaS, IDE or agent fleet. Browser Chat implements directly using authorized tools. GitHub Connector handles remote GitHub changes and evidence independently; Local Bridge handles bounded local jobs; neither grants permissions to the other. The approved adaptive flow has two implementers: Codex running in the terminal, or ChatGPT Browser directly using Project OS v3 tools. Local Bridge is the controlled local-access tool; the terminal is an execution environment, not an implementer. Browser direct remains available independently of the optional LB-09 candidate.

## Production capability consolidation — technical contract

The PM-ratified product scope, candidate interfaces, priorities and end-to-end acceptance live in [docs/PRODUCT.md](../docs/PRODUCT.md#consolidación-funcional-de-producción-del-local-bridge), based on [LB-PRODUCT-20261126-CAPABILITY-CONSOLIDATION-01](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7185110551). The frozen MVP below describes demonstrated scope, not the production feature ceiling. PROJECT_OS.md remains the methodology authority.

Technical constraints for the product capabilities: use typed, bounded operations, private resource mappings, per-resource authorization and dedicated credentials; no arbitrary shell, ADB shell, filesystem access, user-controlled command strings or duplicate remote Git operations. Reuse the existing reader, authenticated jobs, durable ownership, idempotency, grants, exclusivity, status/evidence/cancel and recovery; no parallel engine or registry. Running-job cancellation requires safe lifecycle semantics. Long-running work returns durable identity; evidence binds exact revision, profile, exit/result and artifact digest with bounded/sanitized outputs and explicit incompleteness/failures. For Android, verify the tested bytes before installation and retrieval and define the authorized delivery channel rather than assuming MCP transports binaries. Preserve unrelated worktree changes and reconcile before switching implementers. Candidate interface names are not frozen APIs.

Implementation, disposable/CI validation and reviewed stopped-unit maintenance do not imply real activation. A completed verified normal rollback may be archived intact under the existing maintenance fence and locks. Per the [PM capability-gate decision](https://github.com/codefusion-repo/project-os-v3/issues/14#issuecomment-7188545344) as updated by the [WSL-only decision](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7233893145), apply the effective transport, authentication, credential, review, maintenance, resource-grant, privacy, provenance, bounds and audit controls relevant to each operation. No additional infrastructure certification is required for the trusted local environment. Product scope grants no additional resource access, execution, installation or release permission.

The [remote maintenance outcome #48](https://github.com/codefusion-repo/project-os-v3/issues/48) adds observed installed receipt metadata to authenticated health, plus typed update/status/rollback via a separate one-shot user-systemd service. It reuses the existing local maintenance coordinator, requires explicit owner-private opt-in and the authenticated single operator, checks canonical main/CI and the probe's exact run-attempt wheel evidence before quiescing, independently verifies the wheel during installation, persists request/result identity and preserves the recovery chain. No second permanent daemon, arbitrary commands, paths or URLs. Local readiness is not remote OAuth readiness; the same MCP cannot report while stopped, and local recovery is mandatory if it fails to return. See [operation and opt-in](README.md#browser-maintenance-opt-in). The [bounded NET-05 extension](WSL-VALIDATION.md#finite-network-acceptance-and-evidence-reuse) applies only to this reviewed single-operator non-fixture maintenance capability on the same still-applicable network baseline, not a LAN isolation PASS. Review and effective preconditions precede explicit local enrolment for authorized dogfood; operational acceptance precedes routine use. Candidate code and tests do not authorize real activation. No new permission follows for repository writes or untrusted jobs.

The first LB-07 disposable package slice uses the existing fixture CLI, GitFixture and durable jobs to prepare an exact fixed source revision, validate its data and build a digest-bound ZIP. It does not execute repository code. The project-agnostic preparation contract reuses the private registry and separate preparation/materialization/profile grants. Flutter and Expo/React Native are reference descriptors, not core dependencies. It checks exact local commit/layout and can materialize bounded verified Git blobs into a private job workspace, preserving the original checkout. Common artifact evidence records kind, name, size and digest. Candidate saved text edits reuse prepare/execute jobs with a separate workspace_change grant, exact old-byte digest, bounded normalized inputs persisted for idempotency, private staging and complete snapshot adoption. No original checkout writes or arbitrary patch command. The candidate workspace_changes read returns a bounded historical diff for authorized applied edits, reconstructed from the exact commit and persisted change input, verified against durable evidence. Operational execution and live acceptance remain pending.

The direct WSL execution contract uses registered Flutter analyze/test and Expo typecheck/test commands, plus the QA build profiles, through the existing workspace_execute workflow and sequential worker. Reuse installed SDKs and dependency locks, follow the central resource-reuse rule and retain exact revision, toolchain, lockfile, exit and artifact evidence. Do not expose arbitrary commands or silently substitute another execution path. Stop on uncertain effects; reconcile without replay.

Historical mobile CI evidence (not proof of the replacement WSL backend): runs 45843649406, 45848414057, 45850446739 and 46053081126. The previous execution implementation and its specific acceptance requirements are superseded by the WSL-only decision. Their history remains in Git and the original runs.

Direct execution must be wired into the existing authenticated worker and authorization policy, with functional regression tests and real WSL dogfood. The historical execution evidence does not establish completion of this migration.

## Methodology invariant

Local Bridge is an optional capability provider, not a replacement for the Project OS coordination methodology. All agents must preserve the versioned rules, workflows, skills, templates and adapters specified in [PROJECT_OS.md](../PROJECT_OS.md), regardless of execution provider. GitHub artifacts must use the applicable template and verified evidence; local job success does not waive review, authorization or closeout gates. No provider may silently change the pinned methodology version of an adopted repository.

## Approved adaptive execution architecture

The PM approved this direction on 2026-11-24 (LB-ARCH-20261124-29, [#8](https://github.com/codefusion-repo/project-os-v3/issues/8), [#18](https://github.com/codefusion-repo/project-os-v3/issues/18)). Browser Chat remains the orchestrator and reviewer, uses Project OS v3 tools for authorized terminal interaction, and is the direct implementer when Codex is unavailable or its quota is exhausted in auto mode. Codex runs in the terminal as implementer only with explicit authorization, verified availability and remaining capacity. Strategies: auto (prefer eligible Codex, otherwise browser), browser (direct), codex (explicitly authorized Codex; no implicit fallback). No extra user-facing menu or command family. A router is a small selection policy, not a second workflow engine. Quota exhaustion must be based on verified signals, not guessed from arbitrary error text. Before switching executors, reconcile issue/PR, branch and full HEAD, pending diffs, job state, tests and uncertain side effects. Never run both against the same worktree; stop if previous execution cannot be verified. Same policy and security gates apply to both. No automatic retry of uncertain effects. The LB-09 candidate implements the optional provider and routing; live enrollment and dogfood are not established by the source alone. Use GitHub Connector and registered Local Bridge handlers directly when applicable.

## User experience

First-run setup asks how the operator works (terminal, ChatGPT or both), reuses dependencies, and offers optional components with explicit approval. The original permanent installation is preserved and updated using [single-installation maintenance](README.md#single-installation-maintenance), per [PM decision](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7159966742); no permanent installation per PR or issue. LB-03 guides the operator to connect, configure and verify required Project OS tools using existing components, not a new UX architecture; OAuth and transport validation is tracked in LB-05. See [#12](https://github.com/codefusion-repo/project-os-v3/issues/12) and [#14](https://github.com/codefusion-repo/project-os-v3/issues/14). External OAuth consent and system changes remain operator-controlled. The PowerShell wrapper and optional private HTTPS service preparation are implemented. LB-03 completed with real WSL2 CI and disposable rollback evidence ([closeout](https://github.com/codefusion-repo/project-os-v3/issues/12#issuecomment-7151195379)); applicable supervised service controls remain tracked in LB-05; no automatic activation.

## Capability boundary

- GitHub Connector: authorized reads, commits, PR and checks; closeout under PROJECT_OS.md.
- Authenticated bridge: fixed probe, job status/evidence/cancel, authorized GitHub and methodology readers, and registered local capabilities as implemented. [Operational diagnostics](README.md#operational-diagnostics-lb-05) return fixed sanitized sections. No arbitrary remote shell, arbitrary paths, patches or device tools.
- SQLite stores owner, request key, workflow, resource, result and transitions. Replay returns the same job; interruption is not auto-retried.
- The operator's real repo work can proceed directly via GitHub Connector while local real-resource capability is blocked. Do not pretend a local test ran or use an agent fallback without authorization.

## Pilot sequence

1. Verify the reviewed full SHA and applicable CI jobs. Use the existing central installation and hash-verified maintenance procedure; preserve private state and rollback chain.
2. Verify current authenticated HTTPS health, authorized project/profile grants. Reuse existing WSL toolchains; do not provision a second execution environment.
3. Exercise registered Jobs through submission, status, evidence, idempotent replay, restart persistence and grant revocation. Use bounded functional tests before the authorized real Flutter and Expo dogfoods. Do not expose tokens or private signing material in logs.
4. Dogfood the authorized real issue through GitHub Connector and the registered local execution path. Verify the exact signed artifact and private delivery; report unavailable tests rather than claiming success.

Resend notifications with a link, not an attachment, remain deferred until after LB-09. No Metro, emulator prerequisite, public release or binary committed to Git. The adopted project declares its toolchain, dependency lock, native/managed layout and public QA configuration; Flutter and Expo profiles reuse the same execution and evidence contract; execute directly in AgentsUbuntu through the existing sequential worker. No repository-specific core code or silent fallback. Preserve native source; managed prebuild occurs only on a separate disposable workspace. Keep signing keys and scoped Drive credentials outside project build inputs, Git and logs. Preserve certificate, application identity, version compatibility, signature, both ABIs and final digest. Upload the exact verified signed APK to an authorized private Drive folder from the central trusted delivery boundary. **Android Build v1 candidate build stage.** The explicit project-scoped profiles flutter-apk-qa and expo-apk-qa build release for arm64-v8a+x86_64 on the existing sequential worker. A reviewed private binding includes a qa object: Flutter accepts public dart_defines and optional build_number; Expo accepts native (native, managed-expo, managed-script) and public_env (EXPO_PUBLIC_ only). Configuration is not a caller command; its digest is persisted with each execution. Expo managed generation runs on the disposable copy with unchanged lockfile and offline caches, using the project CLI or existing prebuild script. Current scope is repository-root standard app output and npm/pub locks, not arbitrary flavors, package managers or monorepo layouts. Reuse compatible installed WSL SDKs, dependencies and templates. The build-stage artifact is explicitly unfinalized: it is not attested as an installable QA APK, even if the build command succeeds. The local verified_qa_build_input helper checks ownership, exact revision, cleanup and recorded byte identity before returning bytes to a future trusted finalizer. It is not an MCP download or GitHub upload handler. Persistent QA signer, final signature/package/ABI/version validation, acquisition, transport and real dogfood remain outstanding; no keys are mounted or generated by this change. Production remains unregistered. Historical tests use synthetic bytes and mocked execution, not real QA builds.


**Android Build v1 local finalizer candidate.** `android_qa.finalize_qa_build` takes only the verified terminal build input from Jobs. An explicitly reviewed local caller supplies the trusted JDK/Android SDK and expected QA package; these tools sign/inspect bytes only, never execute project code during signing. The build target is direct WSL execution. The existing worker lock protects persistent per-repository QA identity and final receipt adoption. The key is generated once in private state, not in the checkout, logs or project process. Missing or inconsistent existing identity fails closed; retain it in local backup. The finalizer validates package, non-debuggable release, versionCode monotonicity, both ABIs, alignment and exact certificate, then atomically adopts signed bytes and receipt. Replay verifies bytes and does not re-sign. No production key or distribution. This is an internal local helper, not automatic startup wiring, MCP or publication; trusted SDK admission, real signing tests, local orchestration and an authenticated private transport to the producing PR remain pending. Unit regressions use mocked tools and synthetic bytes, not real signed APKs.


**Supervised QA finalization candidate.** Each operational QA profile requires `qa_signing` in its existing private execution binding: `package`, `java_home`, `build_tools`, pointing to explicitly reviewed trusted local tools (not a checkout). The signer binding digest is fixed in the job alongside the QA recipe. The existing sequential worker finalizes successful builds after verified execution completion and before dispatching the next job; no additional worker or public command. A private atomic receipt permits restart recovery without re-signing; the existing Jobs result records a separate `qa_finalization` outcome, not a fabricated build failure or published artifact. Failed/denied finalization is recorded and not automatically retried. Prior signed history prevents silent key replacement on identity loss. No automatic enrollment, no production. Mocked regression is not proof of Android toolchain signing or delivery. Private transport still requires an actual authorized channel; GitHub REST artifacts do not offer local upload. No public URLs or release workaround.


**Real signing and delivery input validation.** The existing probe CI runs a small synthetic Android packaging fixture using preinstalled SDK/NDK/JDK (no Flutter/Expo re-acquisition); Build output is mocked only for this test. Actual worker finalization exercises signing two versions with the same QA certificate, alignment, ABIs, exact digest, reopen/replay and negative delivery checks. This is not device QA or a real application build. `verified_qa_delivery_input` is a local-only boundary returning the exact signed APK and durable receipt, rejecting cross-repository, stale or uncommitted snapshot inputs and byte tampering. The publisher still needs a real private authorized channel and live PR HEAD check. No artifact upload API is invented, no release or public storage substitute, no APK bytes in MCP. A single APK is produced without v4 sidecar. The real signing fixture passed CI 46065783903; This signing evidence does not establish live Drive delivery.


**Delivery transport status:** the PM selected private Google Drive as the central QA delivery channel (https://github.com/codefusion-repo/project-os-v3/issues/16#issuecomment-7228057104). No GitHub APK delivery runner, ZIP or producer workflow. Implement scoped OAuth and authorized folder binding, exact upload/readback verification, durable reconciliation and authenticated PR link. [Decisión PM](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7236764316): prioridad LB-09 → #60 → LB-08, LB-05/LB-07 completados. `submit_codex_job` reutiliza la cola workspace_execute, su fence y el worker. Codex explícito bloquea; después de una ejecución incierta no hay fallback automático. Resultados de proceso, HEAD/branch y digest del diff permiten review, no sustituyen el diff y CI remotos. No se exponen eventos crudos. Activación y dogfood real pendientes.
