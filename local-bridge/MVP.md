# MVP contract — one installation, one operator

Project OS is a Markdown-first coordination kit, not a SaaS, IDE or agent fleet. Browser Chat implements directly using authorized tools. GitHub Connector handles remote GitHub changes and evidence independently; Local Bridge handles bounded local jobs; neither grants permissions to the other. The approved adaptive flow has two implementers: Codex running in the terminal, or ChatGPT Browser directly using Project OS v3 tools. Local Bridge is the controlled local-access tool; the terminal is an execution environment, not an implementer. Current MVP is browser-direct only.

Time/token savings require measured evidence. Local Bridge specializes in context aggregation and local execution, not generic remote administration or replacement of GitHub Connector. GitHub Connector retains remote code reads/writes, branches, commits, issues, comments, PRs, review evidence, hosted CI and authorized closeout. Use it directly where sufficient. Git may be an internal mechanism for local revision preparation and diff; do not duplicate remote Git tools in MCP. Do not expose arbitrary shell, ADB shell, filesystem access, user-controlled command strings or general administrative execution. Candidate tool names are not frozen APIs: choose the smallest typed interface that delivers each outcome. Context batching, local workspace context, build/validation, Android status/QA/artifact retrieval and optional Codex execution are capability families, not a mandate to create a tool per command.

Reuse existing authenticated job state, idempotency, ownership, resource grants, exclusivity, status/evidence/cancel and recovery; cancellation of running work needs its own safe lifecycle semantics. Long-running work returns durable job identity; evidence links exact revision, profile, result and artifact digest, includes bounded/sanitized output and explicit failures, and must not imply success or completeness on missing evidence. No new workflow engine, parallel registry or implicit grants. For Android preserve the tested bytes and verify the digest before installation and retrieval. Define and verify delivery channel and any visual/log evidence as part of #17 rather than assuming MCP transports binaries.

**Delivery order:** resolve existing maintenance blocker (#14, PR #34), then #15 context, #16 workspace/build/tests, #17 Android QA and artifact retrieval, #18 optional Codex/router, and integral certification/benchmark. Implementation and disposable/CI tests of independent capabilities may proceed without waiting for unrelated phase closure; real activation still requires ALL applicable existing #14, per-resource authorization, host/credential, fresh audit, isolation, profile and review gates. Existing runbooks and security restrictions remain in force. The fixture-only image is not a general-purpose execution environment and does not certify Flutter, Node, Django, Android or Codex. Do not repeat satisfied evidence unless materially changed or stale; fix concrete blockers and tie additional hardening to a risk in the intended deliverable. Keep #8 open until production criteria are met; no release or new local permissions implied.

**End-to-end acceptance:** retrieve issue context, implement using Browser or authorized Codex, prepare exact revision, run real local tests/build, where applicable install/test APK on authorized emulator and retrieve that same artifact, then Browser reviews and completes authorized GitHub workflow. Record actual evidence and measure elapsed time, tool calls, PM interventions, tokens/credits where observable, rework and quality. A green fixture or CI alone is not this product outcome.

## Methodology invariant

Local Bridge is an optional capability provider, not a replacement for the Project OS coordination methodology. All agents must preserve the versioned rules, workflows, skills, templates and adapters specified in [PROJECT_OS.md](../PROJECT_OS.md), regardless of execution provider. GitHub artifacts must use the applicable template and verified evidence; local job success does not waive review, authorization or closeout gates. No provider may silently change the pinned methodology version of an adopted repository.

## Approved adaptive execution architecture

The PM approved this direction on 2026-11-24 (LB-ARCH-20261124-29, [#8](https://github.com/codefusion-repo/project-os-v3/issues/8), [#18](https://github.com/codefusion-repo/project-os-v3/issues/18)). Browser Chat remains the orchestrator and reviewer, uses Project OS v3 tools for authorized terminal interaction, and is the direct implementer when Codex is unavailable or its quota is exhausted in auto mode. Codex runs in the terminal as implementer only with explicit authorization, verified availability and remaining capacity. Future strategies: auto (prefer eligible Codex, otherwise browser), browser (direct), codex (explicitly authorized Codex; no implicit fallback). No extra user-facing menu or command family. A router is a small selection policy, not a second workflow engine. Quota exhaustion must be based on verified signals, not guessed from arbitrary error text. Before switching executors, reconcile issue/PR, branch and full HEAD, pending diffs, job state, tests and uncertain side effects. Never run both against the same worktree; stop if previous execution cannot be verified. Same policy and security gates apply to both. No automatic retry of uncertain effects. Codex provider and routing are deferred, not implemented or invoked in this MVP. Use GitHub Connector and registered Local Bridge handlers directly.

## User experience

Keep the existing selector and central installation. Two entrypoints (Linux/WSL shell and Windows PowerShell via WSL2) use one runtime. No new permanent menu or command family. First-run setup asks how the operator works (terminal, ChatGPT or both), reuses dependencies, and offers optional components with explicit approval. The original permanent installation is preserved and updated using [single-installation maintenance](README.md#single-installation-maintenance), per [PM decision](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7159966742); no permanent installation per PR or issue. LB-03 guides the operator to connect, configure and verify required Project OS tools using existing components, not a new UX architecture; independent host and OAuth certification is LB-05. See [#12](https://github.com/codefusion-repo/project-os-v3/issues/12) and [#14](https://github.com/codefusion-repo/project-os-v3/issues/14). External OAuth consent and system changes remain operator-controlled. The PowerShell wrapper and optional private HTTPS service preparation are implemented. LB-03 completed with real WSL2 CI and disposable rollback evidence ([closeout](https://github.com/codefusion-repo/project-os-v3/issues/12#issuecomment-7151195379)); independent host installation and supervised service certification remain LB-05; no automatic activation.

## Capability boundary

- GitHub Connector: authorized reads, commits, PR and checks; explicit separate closeout authorization.
- Authenticated bridge: fixed probe, synthetic GitHub batch, job status/evidence/cancel; optional fixed Git/Podman fixture with local image binding. LB-05 adds [operational diagnostics](README.md#operational-diagnostics-lb-05), fixed sanitized sections on the reviewed supervised HTTPS instance without fixture, separately opt-in and revocable. No remote commands, paths, image choice, arbitrary patches, real GitHub provider or device tools.
- SQLite stores owner, request key, workflow, resource, result and transitions. Replay returns the same job; interruption is not auto-retried.
- The operator's real repo work can proceed directly via GitHub Connector while local real-resource capability is blocked. Do not pretend a local test ran or use an agent fallback without authorization.

## Pilot sequence

1. Verify the reviewed full SHA and applicable CI jobs; preserve the rejected original and its deterministic historical negative control plus fresh evidence; the exact fixture-only digest is CI-only, not local approval. See SECURITY.md for the ratified R49 policy. Follow WSL-VALIDATION.md for a fresh independent checkout and hash-verified installation. The initial installer refuses an existing venv; subsequent updates use the explicit single-installation maintenance procedure. Preserve the pilot and do not overwrite or migrate private state.
2. Only after independent local rebuild/import and fresh audit of the exact digest under the separately authorized [OCI runbook](OCI-LOCAL-VALIDATION.md), obtain explicit local binding and fixture execution approval. CI-only acceptance is not local approval. Run the fixed fixture in new private state; require SUCCEEDED, negative checks and cleanup evidence; replay and retrieve evidence.
3. For the earlier pilot, restart authenticated HTTP using its existing private state and same approved digest only after local success; for independent validation use new private state and the HTTPS runbook. Reconnect existing tunnel, refresh tools; verify health, submit fixture, retrieve status/evidence, replay and restart persistence. Revoke local opt-in, verify authenticated 403 and no new job, restore explicitly. No tokens in logs.
4. Dogfood a bounded real issue through GitHub Connector directly. Local real resources stay disabled until all gates in SECURITY.md pass. Report unavailable local tests, do not route work to another agent automatically.

## Frozen scope

Complete disposable end-to-end path, security gates, traceability and minimal existing setup. No new infrastructure, central registry, collaborative RBAC, arbitrary shell, auto merge/deploy or additional UI. Android QA, production real-resource grants, lifecycle and independent install certification remain separate production gates; locked dependency evidence is integrated under LB-01, not host certification; source licensing requires maintainer decision. A pilot is not a production release.
