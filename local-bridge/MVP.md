> **Decisión vigente de producto (28-11-2026):** [WSL local como único entorno de ejecución](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7233893145). Las instrucciones OCI/Podman, certificaciones de infraestructura y alternativas de backend de este documento son históricas durante la migración y no constituyen requisitos vigentes. Retirar sus implementaciones y pruebas específicas, reutilizar AgentsUbuntu, el terminal y toolchains existentes. Conservar autenticación/transporte, operaciones tipadas y evidencia, firma y entrega. No interpretar esta nota como implementación efectiva de la nueva ruta.


Project OS is a Markdown-first coordination kit, not a SaaS, IDE or agent fleet. Browser Chat implements directly using authorized tools. GitHub Connector handles remote GitHub changes and evidence independently; Local Bridge handles bounded local jobs; neither grants permissions to the other. The approved adaptive flow has two implementers: Codex running in the terminal, or ChatGPT Browser directly using Project OS v3 tools. Local Bridge is the controlled local-access tool; the terminal is an execution environment, not an implementer. Current MVP is browser-direct only.

## Production capability consolidation — technical contract

The PM-ratified product scope, candidate interfaces, priorities and end-to-end acceptance live in [docs/PRODUCT.md](../docs/PRODUCT.md#consolidación-funcional-de-producción-del-local-bridge), based on [LB-PRODUCT-20261126-CAPABILITY-CONSOLIDATION-01](https://github.com/codefusion-repo/project-os-v3/issues/8#issuecomment-7185110551). The frozen MVP below describes demonstrated scope, not the production feature ceiling. PROJECT_OS.md remains the methodology authority.

Technical constraints for the product capabilities: use typed, bounded operations, private resource mappings, per-resource authorization and dedicated credentials; no arbitrary shell, ADB shell, filesystem access, user-controlled command strings or duplicate remote Git operations. Reuse the existing reader, authenticated jobs, durable ownership, idempotency, grants, exclusivity, status/evidence/cancel and recovery; no parallel engine or registry. Running-job cancellation requires safe lifecycle semantics. Long-running work returns durable identity; evidence binds exact revision, profile, exit/result and artifact digest with bounded/sanitized outputs and explicit incompleteness/failures. For Android, verify the tested bytes before installation and retrieval and define the authorized delivery channel rather than assuming MCP transports binaries. Preserve unrelated worktree changes and reconcile before switching implementers. Candidate interface names are not frozen APIs.

Implementation, disposable/CI validation and reviewed stopped-unit maintenance do not imply real activation. A completed verified normal rollback may be archived intact under the existing maintenance fence and locks; live activation gates remain separate. Per the [PM capability-gate decision](https://github.com/codefusion-repo/project-os-v3/issues/14#issuecomment-7188545344), follow [SECURITY.md](SECURITY.md#gate-matrix) and [WSL-VALIDATION.md](WSL-VALIDATION.md#capability-gate-sequence-both-profiles): bounded GitHub/methodology reads in the reviewed non-fixture profile require effective common host/transport/authentication/credential/review/maintenance controls and exact resource grants, privacy, provenance, bounds, audit and live positive/negative validation. Live OCI job isolation is not their prerequisite; it remains mandatory for subsequent fixture/untrusted execution and integral LB-05 acceptance. Fixture-only OCI evidence is not general-purpose execution certification. Product scope grants no additional resource access, execution, installation or release permission.

## Methodology invariant

Local Bridge is an optional capability provider, not a replacement for the Project OS coordination methodology. All agents must preserve the versioned rules, workflows, skills, templates and adapters specified in [PROJECT_OS.md](../PROJECT_OS.md), regardless of execution provider. GitHub artifacts must use the applicable template and verified evidence; local job success does not waive review, authorization or closeout gates. No provider may silently change the pinned methodology version of an adopted repository.

## Approved adaptive execution architecture

The PM approved this direction on 2026-11-24 (LB-ARCH-20261124-29, [#8](https://github.com/codefusion-repo/project-os-v3/issues/8), [#18](https://github.com/codefusion-repo/project-os-v3/issues/18)). Browser Chat remains the orchestrator and reviewer, uses Project OS v3 tools for authorized terminal interaction, and is the direct implementer when Codex is unavailable or its quota is exhausted in auto mode. Codex runs in the terminal as implementer only with explicit authorization, verified availability and remaining capacity. Future strategies: auto (prefer eligible Codex, otherwise browser), browser (direct), codex (explicitly authorized Codex; no implicit fallback). No extra user-facing menu or command family. A router is a small selection policy, not a second workflow engine. Quota exhaustion must be based on verified signals, not guessed from arbitrary error text. Before switching executors, reconcile issue/PR, branch and full HEAD, pending diffs, job state, tests and uncertain side effects. Never run both against the same worktree; stop if previous execution cannot be verified. Same policy and security gates apply to both. No automatic retry of uncertain effects. Codex provider and routing are deferred, not implemented or invoked in this MVP. Use GitHub Connector and registered Local Bridge handlers directly.

## User experience

The original permanent installation is preserved and updated using [single-installation maintenance](README.md#single-installation-maintenance), per [PM decision](https://github.com/codefusion-repo/project-os-v3/issues/28#issuecomment-7159966742); no permanent installation per PR or issue. LB-03 guides the operator to connect, configure and verify required Project OS tools using existing components, not a new UX architecture; independent host and OAuth certification is LB-05. See [#12](https://github.com/codefusion-repo/project-os-v3/issues/12) and [#14](https://github.com/codefusion-repo/project-os-v3/issues/14). ## Capability boundary

- GitHub Connector: authorized reads, commits, PR and checks; explicit separate closeout authorization.
- Authenticated bridge: fixed probe, synthetic GitHub batch, job status/evidence/cancel; optional fixed Git/Podman fixture with local image binding. LB-05 adds [operational diagnostics](README.md#operational-diagnostics-lb-05), fixed sanitized sections on the reviewed supervised HTTPS instance without fixture, separately opt-in and revocable. This describes the frozen disposable MVP, not LB-06: the integrated real GitHub and versioned methodology readers may be separately enabled in a non-fixture supervised profile under their capability gates. No remote commands, arbitrary paths, image choice, arbitrary patches or device tools.
- SQLite stores owner, request key, workflow, resource, result and transitions. Replay returns the same job; interruption is not auto-retried.
- The operator's real repo work can proceed directly via GitHub Connector while local real-resource capability is blocked. Do not pretend a local test ran or use an agent fallback without authorization.

Resend notifications with a link, not an attachment, remain deferred until after LB-09. No Metro, emulator prerequisite, public release or binary committed to Git. The adopted project declares its toolchain, dependency lock, native/managed layout and public QA configuration; Flutter and Expo profiles reuse the same execution and evidence contract; select reviewed trusted local execution or the existing sequential Podman worker explicitly. No repository-specific core code or silent fallback. Preserve native source; managed prebuild occurs only on a separate disposable workspace. Keep signing keys and scoped Drive credentials outside untrusted builds, images, Git and logs. Upload the exact verified signed APK to an authorized private Drive folder from the central trusted delivery boundary. **Android Build v1 candidate build stage.** The explicit project-scoped profiles flutter-apk-qa and expo-apk-qa build release for arm64-v8a+x86_64 on the existing isolated worker. A reviewed private binding includes a qa object: Flutter accepts public dart_defines and optional build_number; Expo accepts native (native, managed-expo, managed-script) and public_env (EXPO_PUBLIC_ only). Configuration is not a caller command; its digest is persisted with each execution. Expo managed generation runs on the disposable copy with unchanged lockfile and offline caches, using the project CLI or existing prebuild script. Current scope is repository-root standard app output and npm/pub locks, not arbitrary flavors, package managers or monorepo layouts. The image must supply compatible SDKs, dependencies and templates. The build-stage artifact is explicitly unfinalized: it is not attested as an installable QA APK, even if the build command succeeds. The local verified_qa_build_input helper checks ownership, exact revision, cleanup and recorded byte identity before returning bytes to a future trusted finalizer. It is not an MCP download or GitHub upload handler. Persistent QA signer, final signature/package/ABI/version validation, acquisition, transport and real dogfood remain outstanding; no keys are mounted or generated by this change. Production remains unregistered. Tests use synthetic bytes and mocked Podman, not real QA builds.


**Android Build v1 local finalizer candidate.** `android_qa.finalize_qa_build` takes only the verified terminal build input from Jobs. An explicitly reviewed local caller supplies the trusted JDK/Android SDK and expected QA package; these tools sign/inspect bytes only, never execute project code on the host. The build remains exclusively in Podman. The existing worker lock protects persistent per-repository QA identity and final receipt adoption. The key is generated once in private state, not in the checkout, image, logs or project process. Missing or inconsistent existing identity fails closed; retain it in local backup. The finalizer validates package, non-debuggable release, versionCode monotonicity, both ABIs, alignment and exact certificate, then atomically adopts signed bytes and receipt. Replay verifies bytes and does not re-sign. No production key or distribution. This is an internal local helper, not automatic startup wiring, MCP or publication; trusted SDK admission, real signing tests, local orchestration and an authenticated private transport to the producing PR remain pending. Unit regressions use mocked tools and synthetic bytes, not real signed APKs.


**Supervised QA finalization candidate.** Each operational QA profile requires `qa_signing` in its existing private execution binding: `package`, `java_home`, `build_tools`, pointing to explicitly reviewed trusted local tools (not a checkout). The signer binding digest is fixed in the job alongside the QA recipe. The existing sequential worker finalizes successful builds after verified container cleanup and before dispatching the next job; no additional worker or public command. A private atomic receipt permits restart recovery without re-signing; the existing Jobs result records a separate `qa_finalization` outcome, not a fabricated build failure or published artifact. Failed/denied finalization is recorded and not automatically retried. Prior signed history prevents silent key replacement on identity loss. No change to build isolation, no automatic enrollment, no production. Mocked regression is not proof of Android toolchain signing or delivery. Private transport still requires an actual authorized channel; GitHub REST artifacts do not offer local upload. No public URLs or release workaround.


**Real signing and delivery input validation.** The existing probe CI runs a small synthetic Android packaging fixture using preinstalled SDK/NDK/JDK (no Flutter/Expo re-acquisition); Podman output is mocked only for this test.
