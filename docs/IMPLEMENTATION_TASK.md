# Encargo de implementación — Project OS v3

Implementar el MVP descrito en [V3_SPEC.md](V3_SPEC.md) y sus [addenda](V3_ADDENDUM.md), en una unidad cohesiva y sin etapas nuevas. Ante contradicciones, prevalecen las instrucciones más recientes del PM.

- Distribuir seis workflows, nueve skills, catorce templates, dos adapters y selector Python stdlib con tests. El wizard permite buscar workflow primero y solicita repositorio si falta, skills y campos PM opcionales multilínea; persiste solo repo/carpeta en configuración local ignorada. La selección produce un prompt que incluye `repo-context` y `github-traceability` sin duplicados, con aplicación proporcional a su ámbito y es acotado sin copiar el kit, se previsualiza y se guarda de forma segura en la carpeta elegida; los templates son recursos internos; `continue` es default y Markdown directo siempre funciona.
- Hacer operativo el cold start con solo el repo identificado, usando instrucciones y fuentes GitHub vivas para recuperar objetivo, estado, refs, validaciones, blockers y próximo paso. Pedir como máximo un locator primario solo ante ambigüedad material no resoluble; informar límites reales de acceso.
- Compartir los formatos breves de Ejecución, Review y Decisión pendiente y los mismos criterios de evidencia entre superficies. Conservar las relaciones verificables de la unidad y reutilizar issue/PR existentes para implementación, revisión y correcciones. Persistir contexto adicional únicamente cuando aporte valor y esté autorizado.
- Para cambios versionados destinados a integración, reutilizar issue/PR existentes, preparar commit significativo, publicar con autorización/capacidad y verificar SHA remoto, PR y checks disponibles. Sin acceso, permiso o autorización, informar trazabilidad pendiente; una consulta read-only no crea commits y solo un experimento expresamente local y descartable se exceptúa; sin repo tampoco requiere consultas GitHub.
- Si existe unidad GitHub y autorización, añadir y verificar un comentario nuevo por ejecución material, incluidos fallos y bloqueos; no editar historial previo ni sustituirlo con la descripción del PR. Sin autorización o acceso, preparar borrador e informar trazabilidad pendiente.
- Separar preparación, ejecución y verificación. Continuar lo seguro ante incertidumbres secundarias; detener exclusivamente acciones sensibles sin autorización específica. Proteger secretos y no inventar resultados.
- La publicación de este MVP en el repositorio público y su draft PR están autorizados. Merge, release, deploy y configuración sensible no lo están por defecto.
- Ejecutar pruebas reales, registrar comandos y resultados, y conservar explícitamente como pendientes las pruebas de aceptación que necesiten otro chat, agente o superficie si no se ejecutaron. No construir kernel, resolver, catálogo MOS, estado propio, gates generalizados ni handoffs mecánicos.

- Instalar una sola vez con `install.sh`, venv aislado y launcher sin sudo; conservar fallback stdlib y archivos existentes. No guardar perfiles en el kit central ni copiar el kit a proyectos.
- Seleccionar proyecto o workspace, proteger archivos locales con Git antes de escribir, preservar configuraciones desconocidas y facilitar adopción, migración y actualización explícitas mediante un encargo al agente.
- Fijar SHA canónico en AGENTS.md por repositorio, resolver los documentos efectivos desde objetos Git de esa referencia y no atribuir modificaciones locales al commit. Documentar relaciones multirrepositorio solo si son verificables y divulgables.
- Tratar seguridad y protección de secretos como reglas transversales; validar instalador, selección, aislamiento, integridad, regresiones y, cuando esté autorizado y disponible, el recorrido integral con un agente nuevo.
